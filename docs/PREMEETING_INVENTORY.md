# Mandatory native pre-meeting inventory (0.3.1)

This is an independent portable source release, not evidence that a receiving installation has been deployed or a real project has been summarized. No model SDK, model subprocess, external agent or background inference is added. Actual native workers and a live native parent remain necessary.

## State flow

10 completed substantive calculations -> `prepare_meeting` -> sealed inventory -> `meeting` -> 5 separate native participants × 10 synchronized rounds -> structured direction -> next execute request.

Preparation is a separate request under the existing one-active-request-per-run constraint. It is not a calculation or a discussion round. Candidate verification still precedes this boundary; an independently completed original goal needs no further meeting. Existing run counters are not reset. Preparation uses the ordinary lease, fencing, failure, backoff and cancellation protocol. A crash before seal requeues preparation; a crash after seal preserves it, provided sources and goal remain unchanged.

## Parent/native preparation procedure

1. Claim the `prepare_meeting` request; spawn and bind a real native preparation worker using existing claim/bind tools. Never manufacture model output or receipts.
2. Investigate **all accessible existing project results**, including historical packages, later updates, failed routes and current calculation records. Do not restrict the review to the latest ten calculations. Find original materials where available; an index is discovery evidence, not proof that every indexed claim was verified.
3. Declare relevant filesystem `scope.roots`. `prepare_catalogue` recursively inventories all regular files within those roots, hashing their bytes. Explicit exclusions use `{path, reason}` with exact absolute file/directory paths. Symlinks, missing paths and unreadable items are recorded as unavailable rather than silently traversed or skipped. Scope is not a grant of access: obey the host's read restrictions. Exclude live broker databases, scheduler files, meeting discussion/receipt directories and newly generated inventory artifacts explicitly if they lie under a selected project root, otherwise the inventory correctly invalidates itself when those files change.
4. Read the material and author a substantive summary with all five explicit category lists: `accepted_results`, `failed_routes`, `conditional_assumptions`, `open_obligations`, `unverified_findings`. Empty categories are allowed; an entirely empty summary is not. Every item requires `id`, `statement`, `scope`, `verification_status` and nonempty `sources` with exact `path`/`sha256`. Verification status is one of `independently_verified`, `claimed`, `unverified`, `conditional`, `rejected`, `open`. Distinguish full versus mixed/partial scope, reference-flow versus true-flow claims, extra hypotheses, independent-review coverage and unresolved obligations as relevant. Do not promote a local lemma, finite test or reference-flow estimate into a full result.
5. Deduplicate equivalent routes/results. Each stable ID is unique. Optional `duplicate_of` must reference a different known ID and may not create a cycle. Semantic equivalence is the native researcher's responsibility; the broker cannot prove it.
6. Author coverage with `claim` (`scoped_complete` or `partial`), `search_method`, `unavailable`, `excluded`, `caveats`, and `source_dispositions`. Every accessible file must either appear in an item's source references or receive an explicit `{path, reason}` disposition. Accessible material omitted from substantive review should be listed in `coverage.excluded` and force `partial`; source disposition is not permission to hide a gap. Any unavailable/excluded material requires `partial` and nonempty caveats. `scoped_complete` means only the declared accessible scope, never all possible historical material. Catalogue enumeration is mechanically checked; scope selection and semantic completeness are explicit native attestations, not independently certified by Python.
7. Call `seal_meeting_summary(qid, owner, fence, catalogue, summary, coverage, receipt)` using the actual native preparation dispatch receipt. It rechecks all sources, rejects empty materials/stale hashes/missing references/unaccounted files, and refuses unresolved prerequisites. A partial-coverage statement cannot bypass permission. Preparation workers can use `recheck_prerequisite` with actual evidence when an earlier prerequisite has changed.
8. On success the broker writes a fresh append-only summary JSON file with an exclusive create, fsyncs it, stores its hash/bytes/path/provenance in `meeting_summaries`, returns the preparation request and queues the meeting in the same SQLite transaction. Orphan files from an aborted transaction are not accepted seals. Do not overwrite them or a committed seal.
9. Claim the meeting. All five agents receive the same `meeting_context`, including exact sealed summary, hash, path, original goal/input snapshot, and all completed prior-round posts. No reserve/bind/submit/decision is accepted without a valid seal. The existing five-member barrier remains mandatory.

## Invalidation and recovery

Before claim or a discussion operation, the broker rechecks original source file contents, root membership/accessibility, sealed JSON bytes, and goal/input/contract identity. A change durably fences the old request and records cancellation of the coordinator and reserved participants, marks the old meeting `inventory_stale`, and queues a fresh preparation/meeting identity. Historical summaries and posts remain available in export. The exception is raised **after committing** these changes. Reconcile actual native sessions before claiming the replacement.

Ordinary new user inputs and initial contract recording also invalidate dispatches and require a fresh inventory. Pausing/lease recovery without changed inputs or sources retains the sealed summary and already committed posts. Existing 0.3.0 open meetings without summaries are caught by this gate and cannot bypass preparation. Do not reuse their old 50 posts under a new inventory.

Sources are rehashed, not merely checked by modification timestamp. Large project inventories therefore have a real I/O cost. Use precise source roots and explicit documented exclusions; do not silently downgrade validation. Filesystem checks cannot prevent an external writer changing a file immediately after a check; further operations recheck and fail closed. The sealed JSON itself is the immutable historical snapshot, not a live view of the project.

## Safe upgrade procedure

These steps describe a deployment procedure; this source package does not establish that it has been carried out on a receiving installation.

- Review the release code/tests and this protocol. Do not edit or replace the current running source or research home mid-turn.
- Finish the current native computation, preserve its artifacts/checkpoint, and reach a verified quiescent boundary with no claimed requests, unresolved native cancellations or active writers. Record current counts/goal/input versions and code hash. A queued execute may be retained, but run the new code only after all old-code writers have ended.
- Back up the database through SQLite's backup mechanism and preserve the artifact tree/code root. Rehearse additive initialization on an isolated copy using the installer tooling. When upgrading from 0.3.0, the only new table is `meeting_summaries`; upgrading from 0.1.3 adds several tables, as listed in [the installation guide](INSTALLATION.md). Run/goal/input/counter state is not reset, and no mathematical user input is appended for this workflow-only change.
- Switch the parent's configured code root to the reviewed release, initialize the same home with new code at the safe boundary, then inspect status, pending requests and parent actions. Resume with the new native preparation protocol. Verify a real inventory and real 5×10 discussion separately; unit tests are not that evidence.
- Do not blindly downgrade while a `prepare_meeting` request or inventory-gated meeting is active. Old code does not understand that protocol. Stop at a reconciled boundary and plan code/state compatibility; never restore an old database over later research.

The portable package contains no live home or project data. Its tests do not certify a receiving installation, a real project inventory, or real native meetings.
